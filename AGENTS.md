# AGENTS.md

Corm is the brain of Morgan Fetch.

Morgan Fetch is a fully self-contained agent: the `omw` runtime executes a
JavaScript brain inside its embedded Boa JS engine, and the corm service wires
that brain to MCP servers and llama.cpp so the whole thing runs anywhere. This
repo only contains the brain (plus the Nix plumbing to build it); the service
and machine configuration live in the maintainer's `dot` NixOS config. Changes
land through PRs to this repo, get reviewed and merged, and are then pulled into
that config — so this repo is the one controlled path from "the agent wants to
change itself" to "the change exists in the real world."

## Structure

- `src/corm` is the TypeScript package; the pnpm workspace root is the repo
  root.
- `src/corm/src/index.ts` is the entry: it subscribes the agent to the omw
  endpoint and drives the event loop. `src/corm/src/brain.ts` holds the
  provider-fallback and MCP tool loop; `src/corm/src/prompts.ts` assembles the
  system prompt from the markdown in `src/corm/prompts`. `src/corm/esbuild.mjs`
  holds the esbuild config and bundles it into the single unminified
  `src/corm/dist/index.js` Boa script (platform `neutral`, format `iife`, target
  `esnext`, `.md` files loaded as text).
- `src/corm/omw.d.ts` is the hand-written ambient typing for the global `omw`
  host interface; the omw docs are the source of truth.
- `src/corm/prompts` holds Morgan's identity documents (`SOUL.md`,
  `IDENTITY.md`, `USER.md`, `TOOLS.md`, `RUNTIME.md`). The markdown is compiled
  into the brain at build time.
- `src/corm/omw.test.template.toml` is the scaffolded `omw-test` base config
  (generated by `dev scaffold` from the deployment settings).
  `src/corm/e2e/<case>.omw.test.toml` are per-case override fragments;
  `dev merge` deep-merges each over the template and pipes it straight to
  `omw-test run /dev/stdin`.
- `src/nix` is the flake-parts module tree; `flake.nix` imports it with
  `import-tree`, so every `.nix` file under `src/nix` is a module:
  - `pkgs.nix` — the flake `systems` and the shared nixpkgs instantiation
    (`allowUnfree`, `cudaSupport`, the input overlays).
  - `lib.nix` — `flake.lib`: the input/self overlay lists, allowed media
    domains, and the shared bubblewrap bind sets.
  - `dev.nix` — pnpm toolchain, the `corm` package + overlay, the `omw-config`
    package (the deployment settings rendered to `omw.toml`), the `uv` /
    `python312` tooling, and the default dev shell.
  - `dev.nu` — the nushell `dev` command dispatcher.
  - `packages/` — one module per package:
    - `corm.nix`, `models.nix`, `fetchhf.nix`,
      `mcp-server-filesystem-bwrap.nix`, `llama-moe-cache-cuda.nix` (the FATE /
      MoE-cache llama.cpp fork), `omw-config.nix`.
    - `fetchhf.nix` exposes the `fetchhf` overlay, which adds
      `cormPackages.fetchhf` — a fixed-output derivation that snapshots a raw
      HuggingFace repository (`huggingface-cli download`, recursive hash, empty
      placeholder hashes). It parses the checkpoint's `config.json` and surfaces
      the model name, type, architectures and context length on the package's
      `passthru`.
    - `models.nix` assumes the `fetchhf` overlay is present and uses
      `cormPackages.fetchhf` to download raw HuggingFace repositories rather
      than pre-quantized GGUF files. Each backend converts/quantizes those
      checkpoints on the fly before serving.
    - `llama-cpp-convert/default.nix` — the HuggingFace→GGUF converter
      (`convert_hf_to_gguf.py` + `conversion/` + `gguf-py/`) wrapped from the
      FATE fork source, since nixpkgs' `llama-cpp` ships only the C++ binaries.
    - `git-mcp-server/default.nix` — the bun-based `git-mcp-server` package;
      `git-mcp-server/default.nix.lock` is the `bun2nix` lock.
    - `freetoken/default.nix` — the x86_64-only FreeToken module: the Desktop
      AppImage plus the **engine** (`ft` CLI) built with `uv2nix` from
      `pyproject.toml` + `default.nix.lock` (the `uv.lock`). The engine is
      wrapped with `pyproject-nix.util.mkApplication` so only `bin/ft` is
      exposed; the virtualenv stays in the runtime closure.
  - `services/` — the corm NixOS modules. `corm.nix` is the orchestrator: it
    declares `corm.enable`, imports the provider modules, creates the `corm`
    user/group, and defines the `corm.target` unit
    (`wantedBy multi-user.target`, `after network-online.target`). When
    `corm.enable` is true it turns every provider on with `mkDefault true`. Each
    service is `requiredBy`/`bindsTo` `corm.target`, so they come up and go down
    together. The modules are:
    - `gpu-provider.nix` — `corm.gpu-provider` with a `kind` attrTag:
      `llama-cpp` (the FATE fork, `--fate` cache) or `freetoken` (the `ft`
      engine).
    - `cpu-provider.nix` — `corm.cpu-provider`, `llama-cpp` kind on nixpkgs
      `llama-cpp`, with the multimodal projector (`--mmproj`) exported too.
    - `embedding.nix` — `corm.embedding`, `llama-cpp` kind serving embeddings.
    - `omw.nix` — `corm.omw`, a thin wrapper over the omw flake's `services.omw`
      module (imports `inputs.omw.nixosModules.default`). It exposes only
      `variant`, `script` (defaults to the corm package's `index.js`) and
      `envFile`, hardcodes the rest, and builds `services.omw.settingsFile` by
      overriding the `omw-config` package with the provider endpoints/models and
      the agent script (so the service and the scaffolded test config share a
      shape). Every provider runs a `<name>-prepare` oneshot before its serve
      unit: it converts the configured store checkpoint into a writable
      `StateDirectory` (`model.gguf` via `llama-cpp-convert` + `llama-quantize`,
      or `model.ftw` via `ft checkpoint`) and stamps the source path in
      `model.path`, re-converting only when that path changes.

## The brain contract

- The compiled script runs as a plain Boa script and talks to the host through
  the global `omw` (`provider`, `tooling`, `host`). Source may import local
  modules and `.ts` / `.json` / `.md` assets, which esbuild inlines, but must
  not use Node or DOM APIs or rely on runtime module loading.
- Stay within the ECMAScript subset Boa supports.
- esbuild pulls local source modules together into one IIFE; the output stays
  readable and unminified.

## Development

- `dev` is the nushell dispatcher; it has `test`, `scaffold`, `merge`, `format`,
  `lint` and `freetoken`.
- `dev test` builds the script, runs the Vitest unit tests, then merges the e2e
  cases and runs the `omw-test` Boa suite.
  - Unit tests are Vitest projects, one per package: the root `vitest.config.ts`
    globs `src/*/vitest.config.ts`, so each package carries its own config and
    `*.test.ts` files. Vitest must run with `--configLoader runner` because the
    workspace `node_modules` is a read-only store symlink (Vite would otherwise
    try to create `node_modules/.vite-temp`).
  - E2e uses the `omw-test` binary (js variant) from the `omw` flake input,
    which the dev shell provides alongside `omw`. `omw scaffold` and suffix
    discovery are recent omw features, so keep the `omw` flake input fresh and
    reload the dev shell after bumping it.
- `dev scaffold` renders the deployment settings (`nix build .#omw-config`) and
  runs `omw scaffold` over them to (re)write `src/corm/omw.test.template.toml`.
  It introspects the real back ends, so it is best-effort and needs whatever
  environment (secrets, running servers, writable state dirs) would let those
  back ends enumerate.
- `dev format` / `dev lint` run Prettier, nixfmt, Biome, cspell and
  markdownlint; `dev lint` also runs `nix flake check`.

## Nix and dependencies

- The dev shell symlinks the pnpm store into the workspace
  (`symlink-node-modules`). After changing dependencies, run `pnpm-with-reload`,
  then update `pnpmDepsHash` in `src/nix/dev.nix`.
- `nix build .#corm` compiles the script and exposes it as `$out/index.js`; the
  overlay provides `pkgs.corm`. There is no app — the script is not runnable on
  its own.
- `nix build .#omw-config` renders the deployment settings to `omw.toml`; the
  TOML embeds store paths, so building it also realizes the referenced MCP
  servers.
- `nix build .#llama-cpp-convert` builds the HF→GGUF converter wrapper (a Python
  environment with `torch`/`transformers`/`sentencepiece` plus the fork's
  `conversion/` and `gguf-py/`), exposing `bin/llama-convert-hf-to-gguf`. The
  model packages (`.#qwen-3-35b-a3b`, …) are `fetchhf` fixed-output derivations
  of raw HF repos; their hashes are placeholders until filled.
- `nix build .#freetoken-engine` builds the FreeToken engine (the `ft` CLI) with
  `uv2nix`, driven by the vendored `uv.lock`; the output is just `bin/ft`, with
  the virtualenv in the closure. The lock pins PyPI wheels plus the CUDA 13.0
  PyTorch/flashinfer indexes; regenerate it with `dev freetoken lock` and keep
  `uv` / `python312` in the dev shell.
- Toolchain: `nodejs_26`, `pnpm_11`, esbuild 0.28, Vitest 5.
- TypeScript must stay on 6.x. 7.x is the native (Go) port and ships no
  `tsserver.js`, which `typescript-language-server` requires.

## Adding a package

Add it under `src/<name>`, list it in `pnpm-workspace.yaml`, give it its own
`vitest.config.ts` for unit tests, and wire anything needed into
`src/nix/dev.nix`.
